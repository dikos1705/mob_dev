# Shelfwise — подготовка к защите

## Что сказать в начале

«Shelfwise — приложение на Kotlin и Jetpack Compose для личной библиотеки и привычки читать. Это продолжение первой консольной работы, но с Android-интерфейсом, навигацией и сохранением данных. Каталог учебный, выдача локальная. Можно найти книгу, сохранить на потом, взять на полку, записать страницы и заметку, затем посмотреть цель чтения».

## Демонстрация за 3–4 минуты

1. Открой Discover. Введи `Compose`, покажи найденную книгу. Попробуй категорию Design и очисти поиск. Категория и текст поиска применяются вместе.
2. Открой книгу, нажми закладку, затем Borrow book. Покажи Return book и дату возврата. Печатная книга выдаётся на 14 дней, цифровая — на 7.
3. Прокрути до прогресса. Нажми Read 10 pages и передвинь слайдер. Введи заметку и нажми Save note.
4. Перейди в My shelf. Книга есть в Reading и, если сохранена, в Saved. Закончив книгу слайдером, найдёшь её в Finished.
5. Перейди в Progress. Поменяй цель на 500. Покажи, что значение 25 не позволяет нажать Save goal: допустимо 50–5000.
6. Верни книгу через её карточку. Место на полке освободилось, но страницы и заметка остались.
7. Поверни экран с введённым черновиком заметки. Черновик сохраняется. Перезапусти приложение: сохранённые книги, страницы, заметки и цель остаются.

Лимит — три активные выдачи, включая уже дочитанные, но ещё не возвращённые книги. Попытка взять четвёртую показывает сообщение с просьбой вернуть книгу.

## Как устроен проект

- `domain/Models.kt`: модели и чистые правила. Например, `LibraryActions.borrow()` проверяет лимит и возвращает новую `UserLibrary`, не изменяя старую.
- `data/LibraryStore.kt`: интерфейс хранилища и реализация на JSON в приватных SharedPreferences. Запись выполняется на IO-диспетчере. Для такого маленького каталога не нужна отдельная база данных.
- `LibraryViewModel.kt`: принимает пользовательские события, последовательно применяет правила, сохраняет результат и публикует новый StateFlow. При ошибке записи остаётся прежнее состояние и появляется сообщение.
- `ui/ShelfwiseApp.kt`: Navigation Compose, общий Scaffold, нижние вкладки, Snackbar и `collectAsStateWithLifecycle()`.
- `ui/*Screen.kt`: отображение состояния и callbacks; экран не знает, как записывать JSON.

## Частые вопросы

**Почему StateFlow?** Он хранит последнее состояние и позволяет Compose получать изменения. Наружу отдаётся read-only StateFlow, изменять его может только ViewModel.

**Зачем collectAsStateWithLifecycle?** Подписка учитывает жизненный цикл Activity. UI не должен активно собирать состояние, когда приложение находится в фоне.

**remember и rememberSaveable?** `remember` сохраняет объект между рекомпозициями, например SnackbarHostState или результат фильтрации с ключами. `rememberSaveable` дополнительно восстанавливает поддерживаемые небольшие значения через saved-instance state: поиск, фильтр, черновик заметки, ввод цели.

**Что переживает поворот?** ViewModel и его состояние библиотеки остаются при смене конфигурации. Локальные черновики восстанавливает rememberSaveable; маршрут восстанавливает Navigation Compose. После полного перезапуска сохранённые данные загружаются из хранилища.

**Что такое state hoisting?** Компонент получает значение и события вместо владения всей бизнес-логикой. Например, GoalEditor принимает `value`, `onValueChange`, `onSave`, `onDismiss`; решение о сохранении принимает ViewModel.

**Зачем Mutex?** Две быстрые операции «прочитал 10 страниц» не должны обе вычислять результат из одного старого значения. Блокировка сериализует изменение и запись. Для проверки в unit-тесте хранилище специально задерживает сохранение.

**Зачем корутины?** ViewModel запускает сохранение в viewModelScope, хранилище переключает запись на Dispatchers.IO. Отмена корутины не маскируется как ошибка диска. Snackbar показывается в LaunchedEffect.

**Навигация?** Три верхнеуровневых маршрута: discover, shelf, progress. Для карточки используется book/{bookId}. В аргументе передаётся идентификатор; книга ищется в каталоге. Вкладки используют launchSingleTop и сохранение состояния, чтобы не накапливать копии экранов.

**Почему нет сервера?** Задание посвящено Compose, состоянию, ViewModel и архитектуре. Это автономная модель персонального чтения, а не реальная система выдачи. Для реальных пользователей потребовались бы авторизация, серверная проверка наличия и синхронизация.

## Небольшое изменение на защите

- Изменить лимит выдач: `LibraryActions.MAX_LOANS` в `domain/Models.kt`. Сейчас UI и текст сообщения тоже описывают лимит 3, поэтому их нужно согласованно обновить.
- Добавить книгу: новый `Book` в `Catalog.books`; категории вычисляются автоматически.
- Изменить срок выдачи: `BookFormat`.
- Поменять цветовую тему: `ui/Theme.kt`.
- Изменить границы цели: обновить проверку в `LibraryActions.setGoal()` и `GoalEditor`, затем соответствующий тест.

Перед сдачей открой проект в Android Studio и пройди сценарий самостоятельно. Ссылка для сдачи должна вести на ветку `midterm-android`, потому что `main` содержит первую работу.
